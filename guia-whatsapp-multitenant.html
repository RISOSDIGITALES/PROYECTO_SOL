1. Objetivo del proyecto

Actualmente el agente Alex opera en un único número de WhatsApp para una sola empresa (Crating Express), con todos los datos en Airtable. El objetivo es convertir este sistema en una plataforma multi-empresa real, con base de datos propia en MariaDB, donde distintas compañías puedan tener su propio agente de WhatsApp con número propio — personalizado con su catálogo, tono y datos de negocio — sin depender de servicios externos de terceros como Airtable.

Principio central: La lógica del bot es la misma para todos los clientes. Lo que cambia por empresa son los datos de configuración (prompt, catálogo, FAQs, correos). El motor de n8n carga esos datos en tiempo real según quién recibe el mensaje.

Cambia por empresa

  • Número de WhatsApp propio
  • Nombre y tono del agente
  • Prompt del sistema
  • Catálogo de productos/servicios
  • Preguntas frecuentes
  • Correos del vendedor
  • Mensajes de bienvenida y follow-up

Es igual para todos

  • Motor de IA (Groq + fallback)
  • Lógica de recopilación de datos
  • Detección de leads calientes
  • Sistema de follow-up
  • Webhook y flujo en n8n
  • Backend Express + MariaDB

2. Arquitectura general del sistema

Meta WhatsApp API ──webhook──▶ n8n ──HTTP──▶ Express API ──SQL──▶ MariaDB
                                         ▲
                                        Panel web admin

Componentes

ComponenteRolTecnología
Meta WhatsApp Cloud API Recibe y envía mensajes de WhatsApp. Entrega cada mensaje al webhook de n8n. Meta for Developers
n8n Orquesta el flujo: identifica la empresa, llama al API, invoca la IA, envía la respuesta. No almacena datos. n8n self-hosted
Express API Backend propio que expone endpoints REST para leer/escribir configuraciones, leads e historial. Es el único que toca la base de datos. Node.js + Express
MariaDB Base de datos única con toda la información: empresas, configuración de bots, leads, historial de conversaciones, planilla. MariaDB 11 (servidor propio)
Groq IA Genera las respuestas del bot usando el prompt y contexto de la empresa. n8n lo llama directamente. Groq API (llama-3.1-8b)

Por qué esta arquitectura: n8n nunca escribe a la base de datos directamente — siempre pasa por el API. Esto permite que en el futuro se pueda cambiar n8n por otro orquestador, o agregar un panel web, sin tocar la base de datos ni reescribir la lógica de almacenamiento.

3. Meta Tech Provider — qué es y qué necesitamos

Para que una sola cuenta de Meta pueda gestionar los números de WhatsApp de múltiples empresas clientes, se necesita el modelo de Tech Provider con Embedded Signup. Esto no es el BSP (Business Solution Provider) completo — ese requiere contrato formal con Meta y cuotas de volumen. Lo que necesitamos es más accesible:

  • Una Meta App verificada en nuestra cuenta de desarrollador
  • Acceso a Embedded Signup — el flujo guiado con el que cada cliente conecta su número a nuestra app en minutos
  • El cliente mantiene su propia cuenta de WhatsApp Business — nosotros solo tenemos acceso delegado a sus mensajes

Qué pasa desde el punto de vista del cliente final

1
El cliente entra al panel de onboarding
Una página web simple con un botón "Conectar mi WhatsApp Business".
2
Flujo de Embedded Signup de Meta
El cliente inicia sesión con su Facebook Business, selecciona o crea su número de WhatsApp y autoriza el acceso. Todo dentro de un modal de Meta, similar a "Iniciar sesión con Google".
3
El sistema recibe los tokens automáticamente
Meta devuelve el WABA ID, el Phone Number ID y el Access Token. El sistema los guarda en MariaDB y el bot queda activo para ese número.

Pasos con Meta (en orden)

  1. Verificar el negocio en Business Manager → Configuración → Verificación de negocio. Tarda 1-5 días hábiles.
  2. Revisar la app — confirmar que está en modo Live y con los permisos correctos.
  3. Solicitar Embedded Signup — en Meta for Developers, sección WhatsApp → Embedded Signup. Describir el caso de uso: plataforma de automatización de WhatsApp para múltiples empresas. Tarda 1-3 días hábiles adicionales.
  4. Preparar la página de onboarding con el botón que abre el flujo de Meta.

Opt-in obligatorio: Meta exige que el usuario haya dado consentimiento explícito antes de recibir mensajes proactivos (follow-up, notificaciones). Los mensajes reactivos (responder a lo que el cliente escribió) no necesitan opt-in adicional.

5. Schema de base de datos (MariaDB)

Todas las tablas viven en el mismo servidor MariaDB que ya tiene la planilla. Se agrega una base de datos separada whatsapp_platform o se agregan las tablas en la misma base.

Tabla: empresas

Un registro por empresa cliente. Contiene su identidad en Meta y el estado en la plataforma.

CREATE TABLE empresas (
  id                 INT AUTO_INCREMENT PRIMARY KEY,
  nombre             VARCHAR(150) NOT NULL,
  phone_number_id    VARCHAR(50) NOT NULL UNIQUE, -- clave para identificar mensajes
  waba_id            VARCHAR(50),
  access_token       TEXT,                        -- token de acceso de Meta
  activo             TINYINT(1) DEFAULT 1,
  created_at         TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Tabla: wa_config

Configuración del bot por empresa. Aquí vive el prompt, el catálogo y todos los mensajes configurables.

CREATE TABLE wa_config (
  id                     INT AUTO_INCREMENT PRIMARY KEY,
  empresa_id             INT NOT NULL UNIQUE,
  nombre_agente          VARCHAR(80) DEFAULT 'Alex',
  prompt_sistema         LONGTEXT,                 -- prompt completo con {{CATALOGO}}
  instrucciones_ia       TEXT,                   -- reglas adicionales de comportamiento
  catalogo               LONGTEXT,                 -- productos/servicios en texto libre
  faqs                   TEXT,
  msg_bienvenida         TEXT,
  msg_followup_24h       TEXT,
  msg_followup_72h       TEXT,
  palabras_lead_caliente  TEXT,                   -- separadas por coma
  emails_vendedor        TEXT,                   -- separados por coma
  FOREIGN KEY (empresa_id) REFERENCES empresas(id)
);

Tabla: wa_leads

Un registro por contacto de WhatsApp, por empresa. Almacena el estado del lead y los datos recopilados.

CREATE TABLE wa_leads (
  id                 INT AUTO_INCREMENT PRIMARY KEY,
  empresa_id         INT NOT NULL,
  wa_number          VARCHAR(20) NOT NULL,      -- número del cliente final
  nombre_contacto    VARCHAR(150),
  correo_contacto    VARCHAR(200),
  estado             ENUM('Nuevo','Activo','Calificado','Caliente','Completado','Inactivo') DEFAULT 'Nuevo',
  origen             VARCHAR(50),
  datos_recopilados  JSON,                     -- producto, medidas, fecha, etc.
  descripcion_lead   TEXT,
  ultima_actividad   TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  created_at         TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_empresa_numero (empresa_id, wa_number),
  FOREIGN KEY (empresa_id) REFERENCES empresas(id)
);

Tabla: wa_mensajes

Historial completo de mensajes por lead. Permite reconstruir la conversación en cualquier momento.

CREATE TABLE wa_mensajes (
  id           INT AUTO_INCREMENT PRIMARY KEY,
  lead_id      INT NOT NULL,
  rol          ENUM('cliente','agente') NOT NULL,
  contenido    TEXT NOT NULL,
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (lead_id) REFERENCES wa_leads(id)
);

6. API Backend (Express) — endpoints necesarios

n8n nunca accede a la base de datos directamente. Toda operación de lectura o escritura pasa por el API de Express. Estos son los endpoints que el flujo de n8n necesita:

MétodoEndpointQué hace
GET /wa/empresa/:phone_number_id Devuelve la empresa y su config completa dado el phone_number_id del webhook. Es el primer llamado en cada mensaje.
GET /wa/leads/:empresa_id/:wa_number Busca el lead existente. Si no existe, devuelve null (el flujo crea uno nuevo).
POST /wa/leads Crea un lead nuevo con empresa_id, wa_number y estado inicial.
PATCH /wa/leads/:id Actualiza estado, datos_recopilados, nombre, correo, descripcion_lead, ultima_actividad.
POST /wa/mensajes Guarda un mensaje (cliente o agente) en el historial del lead.
GET /wa/mensajes/:lead_id?limit=20 Devuelve los últimos N mensajes del lead para construir el contexto de la IA.
POST /wa/empresas Registra una empresa nueva (llamado desde el flujo de Embedded Signup).
GET /wa/empresas Lista todas las empresas activas (para el panel de administración).

Mismo patrón que planilla: El backend de Express ya existe para la planilla Nicaragua. El módulo de WhatsApp son rutas adicionales en el mismo servidor, conectando a la misma MariaDB. No se necesita un servidor nuevo.

7. Cómo funciona el flujo en n8n

El flujo actual de Crating Express se adapta agregando una capa de identificación al inicio. El resto del procesamiento (IA, envío de mensaje, notificaciones) funciona igual.

1
Webhook recibe mensaje de Meta
El payload incluye phone_number_id (identifica qué número/empresa recibió el mensaje), el número del cliente y el texto.
2
Identificar empresa → GET /wa/empresa/:phone_number_id
n8n llama al API con el phone_number_id. El API devuelve la empresa con toda su configuración: prompt, catálogo, FAQs, access_token, emails. Si no existe, se descarta el mensaje.
3
Buscar o crear lead → GET /wa/leads/:empresa_id/:wa_number
Si el lead existe, se cargan sus datos_recopilados y estado. Si no existe, se crea con POST /wa/leads.
4
Cargar historial → GET /wa/mensajes/:lead_id?limit=20
Se recuperan los últimos 20 mensajes para dar contexto a la IA. Formato compatible con el historial que usa Groq.
5
Guardar mensaje del cliente → POST /wa/mensajes
Se guarda el mensaje entrante antes de procesarlo, para no perderlo en caso de error posterior.
6
Preparar contexto y llamar a Groq
Se construye el prompt con los datos de la empresa (prompt_sistema + catálogo + instrucciones), el historial, los datos del lead y el mensaje actual. Se llama a Groq con fallback igual que hoy.
7
Enviar respuesta por WhatsApp
Se usa el access_token de la empresa (devuelto en el paso 2) para hacer el llamado a la Meta API. El cliente ve el mensaje como si viniera del número de su empresa.
8
Actualizar lead y guardar respuesta del agente
PATCH /wa/leads/:id con estado, datos_recopilados y descripcion_lead actualizados. POST /wa/mensajes con la respuesta del agente. Si es lead caliente, se envía email usando los emails_vendedor de la config.

Diferencia clave vs. hoy: Antes el flujo asumía que todo mensaje era de Crating Express y leía config de Airtable. Ahora el paso 2 hace una sola llamada al API que devuelve todo lo que necesita la empresa correcta, y el resto del flujo funciona igual.

8. Alta de empresa nueva

Una vez que el sistema está en producción, agregar un cliente nuevo toma menos de una hora de trabajo operativo:

Lo que hace el cliente

  • Completa el Embedded Signup (autoriza su número)
  • Proporciona: nombre del negocio, catálogo, FAQs
  • Define el tono y nombre del agente
  • Confirma correo del vendedor para notificaciones
  • Aprueba el prompt del bot

Lo que hacemos nosotros

  • El Embedded Signup inserta automáticamente en empresas
  • Crear registro en wa_config con el prompt personalizado
  • Prueba de mensajes para validar comportamiento
  • Activar el flag activo = 1

Datos mínimos para arrancar un cliente

phone_number_id (de Meta) waba_id (de Meta) access_token (de Meta) Nombre de la empresa Nombre del agente Catálogo / servicios Correo del vendedor Tono (formal / casual)

9. Fases de implementación

FaseTareasPrioridad
1 — Meta Verificar negocio en Business Manager, revisar estado de la app, solicitar Embedded Signup Bloqueante
2 — Legal/Web Crear política de privacidad y términos de servicio. Describir caso de uso para Meta. Bloqueante
3 — Base de datos Crear tablas empresas, wa_config, wa_leads, wa_mensajes en MariaDB. Migrar datos de Crating Express. Alta
4 — Backend API Agregar rutas /wa/* al servidor Express existente. Endpoints de empresa, config, leads y mensajes. Alta
5 — n8n Adaptar el workflow de WhatsApp para que lea del API en vez de Airtable. Probar con CE como primer cliente. Alta
6 — Onboarding Implementar página con botón de Embedded Signup. Flujo automático de registro en la DB. Media
7 — Primer cliente externo Alta de una segunda empresa como prueba real del sistema completo end-to-end. Media

Dependencia crítica: Las fases 1 y 2 requieren aprobación de Meta. Verificación de negocio: 1-5 días hábiles. Embedded Signup: hasta 2 semanas adicionales. Las fases 3, 4 y 5 se pueden trabajar en paralelo mientras Meta procesa las solicitudes.

Migración de Airtable: Durante la transición, Crating Express puede seguir funcionando en Airtable mientras se construye la nueva infraestructura. El switch se hace cuando el backend esté probado — solo se cambia de dónde lee la configuración el flujo de n8n.

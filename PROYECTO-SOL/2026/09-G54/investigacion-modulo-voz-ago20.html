PROYECTO SOL — G54 Platform

Módulo de Bots de Llamada — investigación de arquitectura

Cómo funciona VAPI de verdad por debajo, qué recursos reales usa, y qué necesitaríamos para construir algo propio — pensado desde el día uno como un módulo multiempresa de G54, donde el cliente solo configura (prompt, voz, número) desde nuestra interfaz, sin tocar código.

Investigación · 20 Ago 2026 · actualizado con el alcance real
Corrección de alcance — no reemplazamos el motor de voz, replicamos la capa de configuración
Alcance real del pedido

La primera versión de este documento investigaba cómo construir el motor completo (VAD, streaming, coordinación en tiempo real) — eso queda descartado. El pedido real es más chico y mucho más alcanzable: seguimos usando VAPI (o una API de voces) como motor real de la llamada, y lo que construimos es nuestra propia capa de configuración multiempresa arriba de eso — el mismo tipo de panel que ya existe para WhatsApp Config, pero para bots de llamada. El resto del documento original (presupuesto de latencia, por qué n8n no sirve para audio en vivo) sigue siendo información real y útil como contexto — simplemente no aplica a lo que vamos a construir, porque no vamos a tocar el audio en ningún momento, VAPI se encarga de eso.

⚙️ La API de configuración real de VAPI
Un Assistant es solo un objeto JSON — se crea y edita por API, sin tocar su dashboard
Confirmado en la doc oficial

POST https://api.vapi.ai/assistant (y PATCH /assistant/{id} para editar), con Authorization: Bearer $VAPI_API_KEY — la forma real:

{
  "name": "Bot de [Empresa]",
  "firstMessage": "Hola, gracias por llamar a [Empresa], ¿en qué te puedo ayudar?",
  "model": {
    "provider": "groq",              // ya lo usamos hoy en Marco Voz
    "model": "llama-3.3-70b-versatile",
    "messages": [{ "role": "system", "content": "...el system_prompt real de esa empresa..." }]
  },
  "voice": {
    "provider": "11labs",            // o Cartesia, PlayHT, etc.
    "voiceId": "onwK4e9ZLuTAKqWW03F9" // elegible desde un selector con muestra de audio
  },
  "transcriber": { "provider": "deepgram", "model": "nova-2", "language": "es" }
}

Confirmado: VAPI acepta Groq como proveedor de modelo directo — no hace falta contratar OpenAI ni Anthropic para el LLM, seguimos con lo mismo que ya usa Marco Voz hoy.

El patrón que de verdad conviene — un asistente "genérico" que VAPI configura al vuelo en cada llamada, no uno por cliente guardado a mano
Esto es lo que recomiendo construir

VAPI tiene un mecanismo pensado exactamente para esto: si a un número de teléfono no le asignás un assistantId fijo, cada llamada real dispara un webhook assistant-request a un servidor nuestro, con los datos de la llamada (número marcado, número del que llama) — y esperamos, con un límite de 7.5 segundos, que le devolvamos el objeto completo del asistente a usar para esa llamada puntual.

Esto es exactamente el mismo patrón que ya usamos en toda la plataforma — Sales AI Motor resuelve el system_prompt real por phone_number_id, Community AI lo resuelve por page_id. Acá sería idéntico: número de teléfono real de la llamada → resolver company_id → leer su config de voz en G54 → devolvérsela a VAPI en la respuesta del webhook, armada al vuelo. Nunca hay que crear ni mantener sincronizados N objetos Assistant guardados — un solo webhook en n8n sirve a cualquier cantidad de clientes, cada uno con su propio número real.

Llamada real entra a un número de un cliente
  → VAPI dispara "assistant-request" a nuestro webhook n8n (HTTP normal, no streaming)
  → n8n: resuelve company_id por el número marcado → lee la config de voz en G54
    (mismo patrón exacto de WA Config: system_prompt, voz elegida, primer mensaje)
  → n8n responde el JSON del assistant armado con esos datos (dentro de los 7.5s)
  → VAPI toma esa config y recién ahí arranca la llamada real — el audio en sí
    nunca pasa por n8n ni por nuestro servidor, solo la configuración

Con esto, editar el prompt o la voz de un cliente desde el panel de G54 no requiere ningún llamado a la API de VAPI — el cambio se aplica solo, porque cada llamada nueva vuelve a preguntar. Cero riesgo de que un cliente edite su config y quede desincronizada con lo que realmente tiene guardado VAPI.

Único límite real encontrado — VAPI no es multiempresa de fábrica
A tener en cuenta, no bloqueante

Confirmado con comparativas de agencias que ya pasaron por esto: la API de VAPI opera a nivel de una sola cuenta/organización — no tiene un concepto nativo de "sub-cuenta por cliente" con aislamiento de costos o datos. Todos los números y toda la actividad de todos nuestros clientes conviven bajo nuestra misma cuenta de VAPI.

Esto no es un problema nuevo para nosotros — es exactamente la misma responsabilidad que ya asumimos con Meta/Groq/todo lo demás: el aislamiento por empresa (que un cliente nunca vea ni toque los datos de otro) ya vive en G54 vía company_id, no en el proveedor de turno. El webhook assistant-request resuelve esto de forma nativa (cada número de teléfono es de un solo cliente real), así que el riesgo de mezcla es bajo — pero si en algún momento se quiere medir cuánto gasta cada cliente en llamadas, hay que construirlo nosotros (guardar el costo real de cada llamada en G54 al terminar, no confiar en que VAPI lo separe solo).

Números de teléfono — también por API, sin tocar el dashboard de VAPI

POST /phone-number — importa un número real de Twilio (o Vonage) a la cuenta de VAPI. Con el patrón de assistant-request de arriba, no hace falta asignarle ningún assistantId fijo al número — se deja "abierto" para que cada llamada resuelva su propia configuración. Esto significa que dar de alta a un cliente nuevo es: comprar/asignar un número real de Twilio → un llamado a la API de VAPI para importarlo → guardar en G54 qué company_id corresponde a ese número — 3 pasos, ningún código nuevo por cliente.

🧩 Contexto — qué es VAPI por debajo (para entender por qué su API de config funciona así)
No es "un bot" — es una capa de orquestación sobre 4 servicios de terceros
Confirmado con el propio blog técnico de VAPI y comparativas del mercado
Hallazgo central

VAPI no tiene su propia IA de voz — es el "pegamento" que conecta 4 piezas que ya existen en el mercado, todas intercambiables:

☎️ Telefonía
Twilio / Vonage / SIP → 🎙️ STT (voz→texto)
Deepgram / AssemblyAI → 🧠 LLM
OpenAI / Anthropic / Groq → 🔊 TTS (texto→voz)
ElevenLabs / Cartesia / PlayHT

Esto ya lo sabíamos parcialmente por nuestro propio uso de VAPI — Marco Voz usa Groq (llama-3.3-70b-versatile) como LLM y una voz de ElevenLabs, con VAPI en el medio orquestando y Twilio como la línea telefónica real. VAPI mismo lo dice explícito: su filosofía es "tratar la voz como un problema de ingeniería", dándole al que la construye el control de elegir cada pieza de la cadena.

Lo que sí construyeron ellos, y es la parte difícil de verdad: el motor que coordina las 4 piezas en tiempo real sin que se note el empalme — streaming en paralelo en vez de esperar cada paso, detección de cuándo el cliente terminó de hablar, y cortar la respuesta del bot si el cliente vuelve a hablar. Eso es lo que hace que suene natural en vez de una máquina de "grabá tu mensaje después del tono".

Escala real, para tener una referencia de tamaño

VAPI conecta 14+ proveedores por detrás de una sola capa, procesa unos 62 millones de llamadas por mes, con un SLA de 99.99%. Cobra $0.05–$0.13/min solo por su orquestación — sin incluir telefonía, STT, LLM ni TTS, que se pagan aparte a cada proveedor.

⏱️ Por qué esto es genuinamente difícil (no es "conectar 4 APIs")
El presupuesto de latencia — la conversación humana no perdona
El corazón del problema

En una charla real, la pausa entre que uno termina de hablar y el otro responde es de 200-300 milisegundos. Pasado el medio segundo, ya se siente lento; pasados los 3 segundos, la persona se desconecta de la llamada. Un pipeline bien afinado apunta a ~600ms totales entre "el cliente dejó de hablar" y "empieza a sonar la primera sílaba de la respuesta":

EtapaTiempo
Red (ida y vuelta del audio)30–80ms
Detectar que el cliente terminó de hablar (VAD + endpointing)150–300ms
El LLM empieza a generar (primer token)150–400ms
La voz sintética empieza a sonar (primer audio)100–200ms

La forma clásica de armar esto — esperar la transcripción completa, después mandarla al LLM y esperar la respuesta completa, después mandarla a texto-a-voz y esperar el audio completo — sumaba más de 4 segundos de silencio muerto entre cada turno. VAPI lo resuelve procesando todo en paralelo, por streaming: la transcripción llega en pedacitos ("necesito...", "necesito hacer...", "necesito hacer una cita..."), y el LLM ya empieza a razonar con esos pedacitos antes de que el cliente termine la frase.

Detectar cuándo alguien terminó de hablar es más difícil de lo que parece

No alcanza con "si hay silencio por X milisegundos, el cliente terminó" — la gente hace pausas naturales a mitad de una idea ("necesito cotizar... *pausa* ...una escultura de bronce"). Si el bot interrumpe ahí, se siente peor que si tarda un poco más en responder. VAPI usa un modelo entrenado para esto (no un simple temporizador) y reporta una reducción del 73% en interrupciones prematuras comparado con un timeout fijo — exactamente el mismo tipo de "adivinar la intención real detrás de una pausa" que ya resolvimos, en otro dominio, con las guardas de plausibilidad de Marco por WhatsApp (ítem 227).

El "barge-in" (que el cliente pueda interrumpir al bot): mientras el bot está hablando, el sistema tiene que seguir escuchando y decidir en menos de 100ms si el cliente empezó a hablar de verdad (no solo un carraspeo o ruido de fondo) para cortar el audio del bot a mitad de frase. Mal calibrado, corta la voz del bot por cualquier ruido; bien calibrado, se siente como hablar con una persona.

📦 Contexto archivado — solo aplicaría si algún día se decide dejar de depender de VAPI no es el plan de hoy
Por qué el motor de audio en vivo no puede vivir en n8n (sigue siendo cierto, pero no aplica a lo que vamos a construir)
Solo si el día de mañana se evalúa reemplazar a VAPI

Con el plan real (VAPI sigue siendo el motor, nosotros solo armamos la configuración), n8n nunca toca un solo paquete de audio — así que esta limitación no nos afecta hoy. Queda documentada porque es información real y útil si en el futuro se evalúa independizarse de VAPI por completo: Twilio manda un paquete de audio cada 20ms (50/segundo por llamada), n8n no tiene soporte nativo para streaming real, y sus buffers binarios no serializan bien en ese escenario. Si ese día llega, la ruta sería un framework open source auto-hospedado (Pipecat, LiveKit Agents o Vocode) corriendo en un servidor propio, separado de n8n — pero es una decisión de mucho después, no algo que bloquee el plan de hoy.

🖥️ Lo que necesitaría el panel de configuración del cliente
Referencia del mercado: ni Retell ni Bland (competidores directos de VAPI) son de verdad "sin código"

Vale la pena saberlo antes de prometer "cero esfuerzo": ninguna plataforma seria del mercado logró que configurar un bot de voz sea tan simple como llenar un formulario y listo — siempre queda al menos un campo de texto libre (el prompt) que define el comportamiento real. Lo que sí lograron es que todo lo demás (voz, número, mensaje de saludo, reglas de escalación) sea un formulario simple — mismo criterio que ya usamos para el WhatsApp Config de cada empresa en G54.

Campos mínimos reales para el panel, con el mismo criterio de "cero hardcode por cliente" del resto de la plataforma:

  • Número de teléfono asignado a la empresa (o traer el propio vía Twilio BYOC)
  • System prompt / personalidad del bot (mismo campo que ya existe para WhatsApp — se puede reusar tal cual)
  • Selector de voz (lista de voces reales de ElevenLabs/Cartesia con muestra de audio para escuchar antes de elegir)
  • Mensaje de saludo inicial
  • Horario de atención / qué hacer fuera de horario (voicemail, transferir, o seguir con el bot)
  • A qué número/correo escalar cuando el bot no puede resolver algo (mismo patrón ya construido para WhatsApp/Community AI)
  • Botón de "llamada de prueba" antes de activar en producción
✅ Veredicto
Viable, y mucho más chico de lo que parecía al principio — es un módulo de configuración, no un motor de voz
Recomendación final

Con el alcance corregido, esto se parece exactamente a los demás módulos que ya existen en G54 — no a un proyecto de infraestructura nuevo. Cuatro piezas concretas:

  1. Sección nueva en el panel de G54 — "Configuración de Bot de Llamada" por empresa, mismos campos que el resto de este documento ya detalla (prompt, voz, saludo, escalación).
  2. Un solo webhook nuevo en n8n — responde al assistant-request de VAPI armando la config al vuelo desde G54, mismo patrón exacto que ya usan Sales AI Motor y Community AI para resolver su config por teléfono/página. Sin servidor nuevo, sin tocar audio, sin salir de lo que n8n ya hace bien.
  3. Un número real de Twilio por cliente, importado a VAPI por API (3 pasos, sin código nuevo por cliente) — dejado "abierto" (sin assistantId fijo) para que el webhook de arriba resuelva la config en cada llamada.
  4. Seguimos usando Groq (LLM) y ElevenLabs/Cartesia/Fish Audio (voz) directo desde la config de VAPI — no hay ningún proveedor nuevo que contratar para esto en particular, más allá de elegir la voz.

El único punto a vigilar, con honestidad: VAPI no separa cuentas por cliente de forma nativa — todos nuestros clientes conviven bajo nuestra misma cuenta de VAPI. No es un bloqueante (el aislamiento real ya lo hacemos en G54 con company_id, igual que con Meta/Groq), pero si en algún momento se quiere facturarle a cada cliente su consumo real de minutos, hay que guardar ese dato nosotros al terminar cada llamada, no asumir que VAPI lo separa solo.

🪜 Pasos principales para construirlo (para cuando se retome)
Orden recomendado, de punta a punta
Guardado para retomar más adelante
  1. Decidir el margen/modelo de negocio antes de tocar código — ¿el cliente paga el costo real de VAPI (~$0.13–0.32/min) tal cual, o le sumamos algo? Es la única pieza no técnica y conviene resolverla primero.
  2. Definir los campos de configuración del cliente: prompt del bot, voz (lista con muestra de audio), mensaje de saludo, y a quién escalar si el bot no puede resolver algo.
  3. Armar el mapeo "número de teléfono → empresa" en G54 — reusar el mismo patrón ya construido para WhatsApp (empresa-by-phone) en vez de inventar uno nuevo.
  4. Construir un solo webhook en n8n que responda al assistant-request de VAPI, armando la config al vuelo desde G54 (con cache corto, sin login de sesión, para no arriesgar la ventana de 7.5 segundos) — sin crear ni guardar ningún objeto Assistant por cliente.
  5. Dar de alta un número real de Twilio por cliente e importarlo a VAPI por API, sin asignarle ningún asistente fijo — para que el webhook del paso 4 resuelva la config en cada llamada.
  6. Probar primero a mano (simulando el payload real que manda VAPI) antes de que exista ningún panel — recién después, una llamada de prueba real.
  7. El panel en G54 al final, no al principio — Walter lo construye una vez que el webhook de n8n ya está probado y con un contrato claro de qué espera recibir.

Dudas reales a resolver antes de venderlo a un cliente: dependencia total de VAPI sin ningún respaldo (a diferencia del chat, que ya tiene Groq→Zhipu); la ventana de 7.5 segundos es un modo de falla más caro que cualquier otro agente de la plataforma (un cliente real se queda en silencio en vivo); y las pruebas de punta a punta van a costar dinero real por minuto, no se pueden simular gratis como con WhatsApp.
